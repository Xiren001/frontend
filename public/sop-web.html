Role Overview

The Web team is responsible for building, testing, and optimizing funnel products at Faszik. Your work spans the full product lifecycle — from initial build setup through testing and into the expansion phase.

You operate within the Funnel Tracker in Myko Ops Hub. Every funnel build you work on must be tracked in the system — no builds exist outside the platform.

Key Responsibilities

  • Create and maintain funnel build entries in the tracker
  • Submit copy for proofreading when ready for language review
  • Complete QA checklists before builds advance to testing
  • Manage the testing phase — monitor performance, document findings
  • Make or escalate kill/expand decisions based on performance data
  • Log all mistakes and quality issues in the Mistake Log
  • Contribute to weekly and monthly reports

3

Funnel Tracker

The Funnel Tracker is your primary workspace. Every funnel build must have an entry here — it is the single source of truth for funnel build status.

Creating a New Build

  1. Navigate to Funnel Tracker in the sidebar.
  2. Click + New Build and fill in all required fields: product name, target language, assigned web team member, and start date.
  3. Set the initial phase to Phase 1.
  4. Attach or link the relevant copy documents in the Copy Review section.
  5. Save the entry — it will now appear in the pipeline view.

Updating Build Status

  1. Open the build entry in the Funnel Tracker.
  2. Update the current phase only when all gating requirements for that phase are met.
  3. Add a note when advancing phases — briefly explain what was completed.
  4. Keep the build entry up to date daily — stale entries affect KPI accuracy for the whole team.
⚠️
Never Skip Phases
Do not manually advance a build past the Proofread phase without proofreader approval. Bypassing quality gates is a recordable mistake.
4

QA Checklist Process

Before any funnel build can enter the Testing phase, a full QA checklist must be completed. The checklist is accessible from within each build entry.

Accessing the Checklist

  1. Open the build entry in the Funnel Tracker.
  2. Click QA Checklist — this opens the build-specific checklist page.
  3. Work through every item sequentially. Do not skip items.
  4. Mark each item as passed, failed, or N/A with a brief note where needed.
  5. Submit the checklist when all items are resolved.

QA Areas Covered

AreaWhat to Check
Page LoadAll pages load without errors; no broken images or missing assets
Mobile ResponsivenessFunnel displays correctly on mobile, tablet, and desktop
Form FunctionalityAll opt-in forms, order forms, and upsell flows work correctly
TrackingPixel fires confirmed; conversion events tracked correctly

Upsells/DownsellsAll OTO pages display correctly and pricing is accurate
Thank You PageConfirmation email and thank you page deliver correctly
🚨
Failed QA Items
If any QA item fails, fix it before advancing to Testing. Log the issue in the Mistake Log if it caused a delay of more than 2 hours.

Testing Phase

Testing is where live traffic data determines whether a funnel will be expanded or killed. Your job during this phase is to monitor performance diligently and document findings accurately.

Launching a Test

  1. Confirm QA checklist is fully completed and build is in Testing phase in the tracker.
  2. Coordinate with the Ads team to ensure traffic is being directed to the funnel.
  3. Set the test start date in the build entry.
  4. Define the test duration and minimum spend threshold with your team lead.

Monitoring During Testing

  • Check funnel metrics daily — conversion rate, revenue per visitor, AOV
  • Monitor for technical issues (broken pages, tracking failures) at least twice daily
  • Document any anomalies or issues in the build entry notes
  • Communicate issues to the Ads team immediately if they affect data quality
  • Update the build entry with key metrics at the end of each test day

Test Completion Criteria

Test DurationAs defined per product type (check your team lead)
Statistical SignificanceSufficient data to make a confident decision
Technical StabilityNo unresolved tracking or page errors in final 48h

Decision Rights

After testing, every build requires a Kill or Expand decision. Decision rights are defined by the authority matrix — not everyone can make every decision.

Decision TypeWho Can DecideNotes
Kill (standard test)Web Team Lead + Ads TeamBoth teams must agree; document rationale
Expand (standard)Web Team LeadDocument expansion plan in build entry
Kill (high spend)Management approval requiredSee approval threshold in Settings
Scale to Winning ProductsManagementNominated by Web Lead, approved by management

Documenting a Decision

  1. Navigate to the build entry and click Decision in the pipeline phase selector.
  2. Select Kill or Expand.
  3. Add a mandatory decision note — include key metrics that drove the decision.
  4. If escalating for management approval, tag the relevant manager and set status to Pending Approval.
📊
Decision Rights Reference
The full authority matrix is available under Decision Rights in the navigation. Review it whenever you are unsure who has the authority to approve a specific action.
7

Mistake Logging

All quality issues, errors, and process failures must be logged in the Mistake Log. This is not punitive — it is how the team improves. Accurate logging is required.

What to Log

  • Technical errors that delayed a build going live
  • Tracking failures discovered post-launch
  • Copy errors that were missed in QA
  • Pipeline phase skips or process violations
  • Data quality issues that invalidated test results
  • Any issue that caused a delay of more than 2 hours

How to Log a Mistake

  1. Navigate to Mistake Log in the sidebar.
  2. Click + New Entry.
  3. Fill in: build ID, date, category, description of what happened, root cause, and corrective action taken.
  4. Be honest and specific — vague entries do not help the team improve.
  5. Submit the entry.
✅
Logging Culture
Logging your own mistakes is expected and respected. Teams with accurate mistake logs improve faster. A team that doesn't log mistakes makes the same ones repeatedly.

Reporting & KPIs

The Web team contributes to and reviews both weekly and monthly reports. Keep your build data current so reports are accurate.

Weekly Responsibilities

  • Ensure all active builds have up-to-date phase and notes before weekly report generation
  • Review the weekly report once generated — flag any inaccurate data to your team lead
  • Attend the weekly review meeting with current status on all your active builds
